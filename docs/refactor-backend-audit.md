# Backend refactor audit

This is the baseline review ledger. Original proposed decisions are retained as review history. The [completed plan](refactor-plan.md), [size/resource follow-up](refactor-follow-up-plan.md), additions ledgers, and [final verification](refactor-verification.md) record the implemented result.

This audit covers all 88 tracked paths under `apps/api/**` and `drizzle/**` at the request's baseline. I read the files in full, including tests and generated migration data, and followed the account, project authorization, publication, artifact, Docker runtime, preview routing, retention, cleanup, logging, and email paths. `README.md`, `CONTEXT.md`, and `docs/deployment-feature.md` supplied the operator and user-visible contracts. The ledger at the end names every audited path.

The backend already has useful seams around publication, retention, preview-route writing, artifact storage, and Docker I/O. A broad rewrite would make the hard parts harder to compare. Work should proceed as small changes with their contract tests beside them. Preserve the current API shapes, account and project behavior, database schema, preview URLs, archive support, Docker Engine integration, proxy behavior, and production deployment layout.

## Findings and order

1. **B1, deployment ID contract drift, complete.** `deployment-publication.ts` generates 12-character deployment IDs using `abcdefghjkmnopqrstuvwxy2345679`. One test and two contract documents described six characters with a different alphabet. I changed the assertion in `apps/api/server/deployments.test.ts` to capture the existing runtime format. The focused deployment suite passed 29/29 tests. The parent assigned `CONTEXT.md:55` and `docs/deployment-feature.md:131,141` to the documentation owner. No production ID generation or data changed.

2. **B2, name project-access permissions, implementation complete.** The old `assertProjectAccess(projectId, actor, manage?, adminOnly?)` made authorization depend on boolean positions. I changed it to accept `'read' | 'manage' | 'admin'` and updated each caller. Semantics remain the same: instance admins bypass project membership checks; readers need membership; managers are denied only when their role is `viewer`; project admins are required for `admin`. The existing behavior for an unrecognized stored member role is preserved: it passes `manage` because the old predicate rejected only `viewer`. `assertCanPublishProject` still requests manage access. The role matrix now covers all three permission levels, instance-admin bypass, unknown stored roles, outsider denial, and missing-project behavior. The focused deployment and project suites passed 54/54 tests; API typecheck passed. No route names, wire shapes, database fields, or error outcomes were intentionally changed.

   Files changed for B2 are `apps/api/server/utils/project-access.ts`, `apps/api/server/trpc/routers/projects.router.ts`, `apps/api/server/trpc/routers/deployments.router.ts`, and `apps/api/server/deployments.test.ts`. The upload endpoint keeps using `assertCanPublishProject`, which now names the permission internally.

3. **B3a, isolate Docker log collection from the reconciler, implementation complete.** Added `apps/api/server/utils/deployment-runtime/log-collector.ts` for cursor state, origin/proxy polling, deduplication, failure capture, and cursor persistence. `DeploymentRuntime` retains `#collectingLogs`, config iteration, removing/status checks, and removal synchronization. The collector receives the engine, root, instance ID, and one append callback. It retains the existing timestamp/index/content/ending fingerprint, 50,000-item cap, cursor JSON path, atomic rename, and 0600 file mode. Added a test that deletion clears the persisted cursor. Runtime and Docker log tests passed 12/12; API typecheck passed.

4. **B3b, isolate Docker container operations, implementation complete.** Added `apps/api/server/utils/deployment-runtime/containers.ts` with `DockerDeploymentContainers`. The collaborator receives the engine, instance/network identity, proxy image, storage root, `ArtifactStore`, and a narrow runtime-service getter. It owns image resolution/pull/existence, create payloads, ownership labels and host config, static archive/config installation, proxy config generation/install, health HTTP probes, inspection, ownership assertion/removal, and stop. `DeploymentRuntime` retains image choice, operation order, desired-state/removal checks, health bookkeeping, start/rollback orchestration, log capture, locks, reconciliation, orphan scan, and artifact cleanup. Existing public runtime fields and `createStaticOriginNginxConfig` export path remain available. Runtime/log suites passed 12/12 and API typecheck passed. Live Docker lifecycle/Nginx suites passed 12/12 after extraction.

5. **H1, add a server query for searchable and sortable deployment history/audit, implementation complete.** Current `deployments.history` remains unchanged; separate `deployments.audit` supports project/deployment scope, offset/limit (defaults 0/20, max 100), trimmed search, event/actor filters, four whitelisted sort columns with asc/desc direction and stable ID tie-break. It returns `{ entries, total, events, actors }`, with options computed across the whole selected scope and deleted actor snapshots retained. Search covers event, deployment ID, actor name and ID, and JSON details; no credential or secret tables participate. The expanded suite covers cross-project non-disclosure, viewer/outsider access, scoped filter options, deleted snapshots, actor-name/ID/deployment-ID/details search, event and each sort column in both directions, tie-break order, filtered totals, and pagination beyond 100 rows. Deployment tests passed 32/32 with H1 and R1 coverage; API typecheck passed.
6. **R1, expose captured credential selection and guard reuse, approved and implemented.** Add only the opaque captured `registryCredentialId` to `PublicDeployment.config`; never add credential names or authentication material. During reuse, an omitted selection preserves the captured ID and auth (including when the original saved credential was deleted), `null` explicitly clears both for a public image, and a string selects another existing project credential and captures its auth. Reject reuse of cleanup-pending or already-cleaned source deployments while preserving reuse of failed deployments whose content remains. Keep the existing project defaults and source deployment capture behavior. Tests cover all three selection states, absence of secret values in public summaries, and cleanup/cleaned reuse rejection.

7. **B4, reduce repeated route availability reads, implementation complete.** `getPreviewRouteTargets()` now retains the rows from its existing eligible-deployments query and derives both the available-ID set and deployment routes from those rows. The predicate and returned fields/order remain unchanged. Deployment-addresses and preview-route publisher tests passed within the 86-test backend group; API typecheck passed.

8. **B5, split project invitations into a procedure group, implementation complete.** Added `apps/api/server/trpc/routers/project-invitations.procedures.ts` exporting the four procedures as one object, spread into `projectsRouter` so the `projects.*` names and inferred types remain intact. `projects.router.ts` keeps identity, settings, membership, and project access work. The group preserves Better Auth admin/member branches, email failure rollback, pending/expiry/verified checks, inviter snapshots, sorting, joins, and counts. The projects/setup/auth group passed 53/53; API typecheck passed.

9. **Z1, reuse shared account/project schemas in backend validation, implementation complete.** Setup, signup completion, password reset, project create/rename/suggest, invitation email, and Better Auth project hooks now use the corresponding exports from `apps/api/shared/validation.ts`. `project-options.ts` maps schema failures through its existing `APIError` message; duplicate preview slugs and host-length errors keep their existing application checks and error types. Auth/project/setup tests passed with B5.

10. **Z2, share deployment tag and preview-slug label validation, implementation complete.** Added `apps/api/shared/deployment-tags.ts` with `deploymentTagNameSchema`; tag assignment uses `safeParse` and keeps the existing BAD_REQUEST response and all subsequent deployment-ID, hostname, health, DB, and route checks. `deployment-addresses.updateProjectPreviewSlug` now reuses shared `previewSlugSchema`, retaining conflict, host-length, rollback, and error behavior. Runtime host parsing remains a defensive boundary.

11. **Z3, derive admin-default and registry-credential Signal Forms from API schemas, implementation complete.** Added adjacent form schemas that validate draft models with Angular `validateStandardSchema`; admin MiB values convert to canonical bytes before API validation, and canonical issues map back to their displayed fields. Registry form fields reuse the same shared validation primitives as the API input. Signal metadata preserves native required/length/number bounds without adding duplicate Angular validators; secret remains required in the add form while the backend's existing empty default and optional update ID remain accepted. The new form schemas have focused conversion and error-path tests; the selected Angular tests passed 15/15 and the production Angular build completed.

12. **Leave generated schema artifacts alone absent a schema change.** `drizzle/schema.ts`, `drizzle/migrations/0000_init.sql`, `drizzle/migrations/meta/0000_snapshot.json`, and `_journal.json` describe a fresh-database-only WIP. The snapshot and SQL migration are generated data. There is no upgrade/backfill path, so casual edits would create misleading migration state. If a selected backend change needs a schema edit, use Drizzle generation and update the initial migration only under the repository's documented fresh-database workflow.

## Invariants to keep visible during refactors

- Project access distinguishes read, manage, and project-admin authority. Instance admins retain project-wide authority even without membership. Pending and removed memberships must not gain access through IDs scoped to another project.
- Setup creates at most one first admin under concurrent requests. The last instance admin cannot be removed or demoted. Signup and password-reset links are one-time, expire, bind to the current user/email, and do not let admins choose another user's password. Public password-reset requests hide whether an eligible account exists.
- Project runtime secrets and captured registry authentication stay encrypted at rest and out of public API summaries. Published deployments capture project settings, runtime values, secrets, registry auth, and instance defaults. Reusing content creates a new deployment identity and snapshot. Container images resolve to immutable digests.
- Static uploads enforce byte and expanded-size limits, safe relative paths, duplicate rejection, regular-file-only entries, supported codecs, and a root `index.html`. Content hashes identify complete directory trees. Shared content remains until no retained deployment references it and no recent pending upload protects it.
- Preview host labels remain DNS-safe. Branch aliases normalize deterministically and collisions fail. Branch selection follows submission order after health readiness. Tags require a healthy running target. Route mutations serialize, publish an atomic Traefik snapshot, await acknowledgement, and restore prior database state if the publication fails.
- Docker operations touch only containers with matching senv ownership labels and do not remove unrelated resources. Readiness checks the owned origin and proxy. Explicit stop state survives reconciliation; restart uses the same snapshot. WebSockets, streaming, proxy route precedence, compression, SPA fallback, caching restrictions, and alias cache isolation remain intact.
- Retention protection comes from pinning, branch selection, or tags. Losing the final protection starts a fresh captured retention period. Removing a deployment persists intent before runtime cleanup, retries interrupted removals on startup, erases runtime secrets/logs/artifact reference only after runtime removal, and retains history. Failed removal preserves the record and resources.
- Log pagination follows append sequence, storage stays bounded by each deployment's captured limits, UTF-8 and line boundaries survive Docker frame splitting, and duplicate polling fragments are filtered without dropping distinct records that share timestamps.
- SQLite stays local to the API, WAL and foreign keys remain enabled, migrations stay the documented Drizzle workflow, and the app/API/migration/Traefik Compose arrangement keeps its current volume and proxy responsibilities.
